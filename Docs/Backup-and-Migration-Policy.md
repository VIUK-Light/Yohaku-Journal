# Yohaku Journal データ保護・バックアップ方針

この文書は、日記とセルフチェックのデータを「利用者が必要なときに持ち出せ、失敗しても現在の記録を失わない」ための設計契約です。広告、利用時間の延長、アカウント登録、クラウド同期を前提にしません。

## 方針の優先順位

1. 現在端末にある記録を守る
2. 利用者が内容を理解してから書き出し・復元する
3. 暗号化されていない記録を共有経路へ渡さない
4. 失敗時はデータを削除せず、原因を表示して再試行できるようにする
5. 互換性のために既存データの意味を推測して書き換えない

## 保存場所と同期

- 保存の正本は端末内のSwiftDataストアです。
- アカウント、サーバー送信、広告SDK、クラウド同期は使用しません。
- SwiftDataのスキーマを変更する場合は、既存の`MoodEntry`、セルフチェック、相談導線に関する記録を読み込める移行手順とテストを先に用意します。
- 保存ストアを開けない場合、一時的な空のデータベースへ切り替えません。現在のデータが見えない状態を「データがない」と誤認させないため、エラーを表示して停止します。

端末内保存は、利用者が自分のデータを管理できるようにするための設計です。端末の紛失・故障に備えるには、利用者自身が暗号化バックアップを安全な場所に保管する必要があります。

## アプリロック

- アプリロックは任意設定です。未設定でも通常の記録機能を妨げません。
- 認証にはOSの端末認証を使い、独自PINや生体情報を保存しません。
- Face ID、Touch ID、端末パスコードなどの可否はOSに委ねます。
- バックグラウンドへ移ると、ロック有効時は記録内容の代わりにプライバシー画面を表示します。
- 認証に失敗しても記録を削除したり、アカウントを停止したりしません。

実装ではAppleの`LAPolicy.deviceOwnerAuthentication`を使います。アプリは生体情報そのものへアクセスせず、OSから認証結果だけを受け取ります。

## 暗号化バックアップ形式

バックアップは`DiaryArchiveV1`として、次のモデルを含むバージョン付きアーカイブにします。

- `MoodEntry`
- セルフチェックの保存記録
- 利用者が明示的に保存を選んだ安全確認の日時

書き出し時の契約：

- パスワードからPBKDF2-HMAC-SHA256で鍵を導出します。
- 反復回数は600,000回、Saltは毎回ランダムに生成し、KDF設定をヘッダーへ保存します。
- 内容はAES-256-GCMで暗号化し、認証タグで改ざんを検出します。
- 暗号化前のJSONや平文アーカイブを一時ファイルとして作りません。
- 共有するファイルは暗号化済みのバックアップだけにします。
- ファイルサイズ、レコード数、文字列長、配列長に上限を設け、異常に大きい入力を復元しません。

AES-GCMのNonceは暗号処理ごとに一度だけ使い、パスワードとバックアップファイルを同じ場所へ保管しないよう利用者へ説明します。パスワードを忘れた場合に復号できる管理者用の抜け道は作りません。

## 復元の手順

復元は、ファイルを選んだ時点では開始しません。次の順序で行います。

1. ファイルサイズと形式を確認する
2. ヘッダーのバージョン、暗号方式、KDF設定、認証タグを検証する
3. パスワードで復号し、必須フィールド・日付・件数・重複IDを検証する
4. 現在のデータとの件数と競合IDをプレビューする
5. 利用者が復元を明示的に確定する
6. 全件を適用し、保存が成功した場合だけ処理を確定する

途中で復号・検証・保存のいずれかに失敗した場合、現在のデータを維持します。復元用の一時的なレコードを画面に表示したままにしたり、部分的に書き換えたりしません。

## 同一IDの競合

同じIDの記録が端末側とバックアップ側の両方にある場合、既定値は「現在のデータを残す」です。バックアップ側で置き換える場合は、件数と対象を表示したうえで利用者が明示的に選択します。

競合解決に「新しい方が正しい」「気分が改善した」などの自動推測は使いません。日時だけで利用者の意図を決めません。

## 全データ削除

- 削除対象の種類と件数を表示します。
- 一度目は確認、二度目は明示的な確定操作とします。
- 保存に失敗した場合はロールバックし、削除前のデータを維持します。
- 削除後に復元できるよう、アプリが秘密のコピーを作ることはありません。
- 暗号化バックアップはアプリの削除対象外です。利用者が別途保管しているファイルは、利用者自身が管理・削除します。

## 互換性と移行

- アーカイブ形式には必ず形式バージョンを持たせます。
- 未対応のバージョンは、部分的に読み込まず安全に拒否します。
- 既存の`recordType`の文字列はそのまま保存し、内部表示への変換だけを行います。
- 不明な旧値を勝手に別の記録種類へ書き換えません。互換変換を追加する場合は、変換前後のテストを追加します。
- 形式を変更するときは、旧形式の復号・読み込み・再書き出しの往復テストを用意します。

## 検証チェックリスト

リリース前に、少なくとも次を確認します。

- 正しいパスワードで暗号化バックアップを往復できる
- 間違ったパスワードでは平文を返さない
- ciphertext、認証タグ、ヘッダーの改ざんを検出できる
- 未対応バージョン、過大な件数、過大な文字列を拒否できる
- 既存のMoodEntry、セルフチェック、安全確認日時が欠落せず復元できる
- 競合の既定動作が「現在のデータを残す」になっている
- 復元途中の失敗で現在のデータが変わらない
- 全削除途中の失敗で現在のデータが変わらない
- バックグラウンド画面に日記本文が残らない
- 独自PIN、広告SDK、クラウド送信、平文の共有ファイルが追加されていない
